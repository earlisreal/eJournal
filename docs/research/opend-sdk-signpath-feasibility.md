# OpenD SDK replacement for SignPath Foundation

Researched 2026-09-17; project decision updated 2026-09-20. **Verdict: technically feasible, not yet an eligibility clearance.** A small Kotlin/JVM client can speak OpenD's documented local TCP protocol and replace the bundled Java SDK for eJournal's four read-only import calls. Removing the SDK removes the clearest non-OSI component from the signed artifact. eJournal will disclose the separate OpenD dependency and independently written adapter in its SignPath application and treat SignPath's decision as the eligibility answer; a separate Moomoo inquiry is not a pre-application gate.

## Evidence and implementation boundary

- eJournal currently packages `com.moomoo.openapi:moomoo-api:10.8.6808` and uses its connection and generated protobuf classes for account list, historical orders, historical fills, and order fees in [`MoomooOpenDClient.kt`](../../shared/src/jvmMain/kotlin/io/earlisreal/ejournal/domain/moomoo/MoomooOpenDClient.kt). The [published POM](https://central.sonatype.com/artifact/com.moomoo.openapi/moomoo-api/10.8.6808) labels this artifact “Moomoo API Code Non-Commercial License Agreement”; its linked `License.txt` is not present in the [linked Java repository](https://github.com/MoomooOpen/java-moomoo-api). Do not treat that jar as OSI-licensed or redistribution-cleared based on another SDK's license.
- Moomoo expressly documents the [underlying TCP protocol](https://openapi.moomoo.com/moomoo-api-doc/en/ftapi/protocol.html) for clients outside its supported SDKs. The 44-byte, little-endian `FT` header carries protocol ID, incrementing serial, body length and SHA-1, and supports protobuf (`0`) **or JSON (`1`)** bodies. Connection initialization (1001) and periodic KeepAlive (1004) are required; the [trade API protocol index](https://openapi.moomoo.com/moomoo-api-doc/en/trade/overview.html) lists eJournal's four read-only requests as 2001, 2221, 2222 and 2225. Their schemas/fields are in Moomoo's [account](https://openapi.moomoo.com/moomoo-api-doc/en/trade/get-acc-list.html), [history-order](https://openapi.moomoo.com/moomoo-api-doc/en/trade/get-history-order-list.html), [history-fill](https://openapi.moomoo.com/moomoo-api-doc/en/trade/get-history-order-fill-list.html), and [fee](https://openapi.moomoo.com/moomoo-api-doc/en/trade/order-fee-query.html) docs. **JSON is the narrowest route:** use the repo's existing `kotlinx.serialization.json` and JDK sockets/digest; no Moomoo protobuf code or new library need be bundled. This is an engineering inference from the documented format, not a tested compatibility claim.
- Moomoo's [official Python SDK repository](https://github.com/MoomooOpen/py-moomoo-api) has an [Apache-2.0 LICENSE](https://github.com/MoomooOpen/py-moomoo-api/blob/main/LICENSE) and publishes [protobuf source files](https://github.com/MoomooOpen/py-moomoo-api/tree/main/moomoo/common/pb). That is evidence for that repository, **not** a license grant for the Java jar, every current schema or all code in Moomoo's downloadable SDKs. Copying/generating from Moomoo `.proto` files or porting upstream client code therefore needs a file/version-specific license and notice review; independent JSON code based on protocol documentation avoids that dependency, though Moomoo's API terms still need confirmation.
- Replacing the client **does not replace OpenD**. Moomoo says OpenD is the necessary separately installed, signed-in gateway that relays local client requests to its servers; eJournal already instructs users to install it and does not bundle it. See Moomoo's [architecture/installation](https://openapi.moomoo.com/moomoo-api-doc/en/intro/intro.html) and [OpenD overview](https://openapi.moomoo.com/moomoo-api-doc/en/opend/opend-intro.html).
- [SignPath Foundation terms](https://signpath.org/terms.html) require OSI-approved licensing for all project components and no proprietary component in the project/signed package (except System Libraries), and permit unsigned **OSS** upstream binaries inside signed packages. They also require signed artifacts to be verifiably built from source. The terms do **not explicitly say** whether optional functionality that connects to a user-installed gateway outside the signed artifact is eligible when that gateway's OSS licensing has not been established. Do not infer that OpenD is a System Library or that merely avoiding its redistribution settles this.

## Effort and risk

The transport is small; preserving behavior is the work: initialization/heartbeat, packet framing and partial reads, serial correlation, disconnect/timeouts, JSON field mapping (especially 64-bit account/order IDs), rate limits, and parity of date/fee handling. Keep the existing `MoomooClient` boundary and four read-only requests; do not implement trade/unlock protocols. Verify with deterministic packet fixtures and a hands-on OpenD smoke test on each release platform. Moomoo documents [encrypted OpenD mode](https://openapi.moomoo.com/moomoo-api-doc/en/ftapi/protocol.html); the current SDK path connects without encryption, so supporting encrypted mode would be a separate scope decision. Estimate is a focused implementation plus integration-testing effort, **not** a dependency swap; no schedule is credible until a JSON handshake and four-call spike succeeds.

## Remaining eligibility questions

1. **SignPath:** If the signed eJournal package contains only eJournal/OSI-licensed components, but its optional importer requires a *user-installed, separately distributed OpenD* process whose OSS license has not been established, does the project meet the “all components/no proprietary code” condition? Does the answer change if OpenD is a documented prerequisite rather than an automatically downloaded dependency?
2. **SignPath:** Is an independently authored client using Moomoo's public protocol documentation acceptable under the “own source code” and verifiable-build rules? If any Apache-2.0 Moomoo `.proto` files or adapted Python code are used instead, what provenance, notices and upstream-file treatment are required?
The following Moomoo questions could reduce legal uncertainty but are not part of the selected application sequence: whether its user/API agreements restrict an independently written read-only client, and which exact license governs current downloadable schemas and generated sources. The implementation avoids those schema/source files rather than depending on an answer.

Treat SignPath eligibility as **conditional** until it accepts the submitted SDK-free boundary. If SignPath rejects the direct OpenD integration, remove it from the signed application, retain Moomoo CSV import, and reapply.
